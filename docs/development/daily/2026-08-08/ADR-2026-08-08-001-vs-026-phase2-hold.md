# ADR-2026-08-08-001: VS-026 — Phase 2 sensor-tool re-scoping decision

- Status: Decided — HOLD, no tool code written
- Date: 2026-08-08
- Related: [VS-026](../../tickets/VS-026-reconsider-descriptor-parser-phase2.md), [VS-023](../../tickets/VS-023-migration-evidence-sensor-tools.md), [ADR-2026-08-07-003](../2026-08-07/ADR-2026-08-07-003-vs-023-sensor-tool-scoping.md) (the original deferral this re-opens), `tests/evaluation/jpetstore-6-detailed-timing-and-citation-2026-08-07.md` (the wrong-file citation run)

## Question re-opened

`ADR-2026-08-07-003` deferred VS-023's five ecosystem-aware sensor tools
(`discover_deployment_candidates`, `inspect_build_runtime`,
`inspect_network_contract`, `inspect_configuration`,
`inspect_state_dependencies`) in favor of one narrow, judgment-free
primitive, `locate_evidence`, and set an explicit revisit signal: Phase 2
becomes worth reconsidering if the narrower primitive's live rehearsal
"still shows fabrication (e.g. because the agent picks a wrong
`glob`/`content_pattern`)." VS-026 asks whether two events since then meet
that signal:

1. A live interactive Detailed run (2026-08-07,
   `jpetstore-6-detailed-timing-and-citation-2026-08-07.md`) cited
   `docker-compose.yaml:17` and `docker-compose.yaml:21` for two
   blocker-level claims (the `openjdk:25` base image and the
   `tomcat90`/`tomcat9` CMD conflict) that are actually sourced from
   `Dockerfile:17`/`Dockerfile:21` — repeated 3x and 4x in the same report.
2. `VS-023`'s "Citation-sourcing enforcement follow-up" section separately
   found `locate_evidence` returning the *first* line matching an
   under-specific `pattern` (`INSERT INTO` matching a non-credential
   `sequence` row before the real `signon`/`account` rows) — a real-but-imprecise
   match, not a wrong file.

## Step 1: was the wrong-file citation tool-sourced or hand-written?

**Undetermined from surviving artifacts — no reproducible trace exists.**
The interactive run that produced the wrong-file citation was not run
through `run_opencode_acceptance.py`'s structured harness (which captures a
`tool_calls` array with every `locate_evidence` call's `glob`/`pattern`/
`reference`); the eval doc records it as an ad hoc `opencode run
--interactive` invocation that reused the harness's setup functions but
not its event capture, because `tmux`/`sqlite3` — the tools
`memory/opencode-e2e.md`'s documented interactive procedure needs to read
`opencode.db` directly — are not installed on this Windows machine. I
searched for a surviving trace before concluding this:

- No `trace.json` for this run exists anywhere under this repo's
  `tests/evaluation/`, the leftover `/tmp/opencode-acceptance-*` directories
  from that session (7 found, all dated 2026-08-07 10:02–10:47, all
  `slash-default-summary` Summary-mode runs unrelated to this Detailed run),
  or the session scratchpad path the eval doc names
  (`<session scratchpad>/detailed-run`, which is ephemeral and no longer
  exists).
- `run_interactive_probe()` (`scripts/run_opencode_acceptance.py:856-924`),
  the harness function whose command line matches what the eval doc
  describes, only ever writes raw `stdout.log`/`stderr.log` text — it has no
  structured `tool_calls` capture at all, so even a surviving log from that
  exact function would not show individual `locate_evidence` arguments.

I cannot honestly report this as "hand-written" or "tool-sourced" — both
remain speculation without the trace. What I can add is a fresh,
trace-backed data point instead of resolving the original one.

## Step 2: reproduction sample

Three live Detailed repeats, `python scripts/run_opencode_acceptance.py
--case slash-detailed --repository-root C:/ktmp/jpetstore-6 --repeat 3
--timeout 300 --model upstage/solar-pro2` (per `memory/opencode-e2e.md`'s
provider fallback — `local-sglang` remains unreachable this session;
connectivity to `https://api.upstage.ai/v1` confirmed with a `200` on
`/v1/models` before spending the run). Target verified at the golden set's
pinned revision (`e1dd9a31d1cef68793cd0933ae06898e6fcfa807`) before and
after, unchanged. All 3 `PASS`, batch `--format json` harness (captures a
full `tool_calls` trace, unlike the original interactive run).

**The specific wrong-file confusion did not recur in 3/3 runs.** Every
repeat correctly cited `Dockerfile:17` for `image: openjdk:25` and
`Dockerfile:21` for the `tomcat90` command/args fields — directly verified
against the real file (`Dockerfile:17` → `FROM openjdk:25`, `Dockerfile:21`
→ `CMD ./mvnw cargo:run -P tomcat90`) — never `docker-compose.yaml:17`/`:21`
for either claim.

**A different, more concrete gap surfaced instead: `locate_evidence` was
called zero times across all 3 runs** (`tool_calls` breakdown: repeat 1 —
`skill`×1, `read`×13; repeat 2 — `skill`×1, `glob`×1, `read`×6; repeat 3 —
`skill`×1, `glob`×1, `read`×4), despite `locate_evidence: allow` in the
run's own permission set and the agent prompt's explicit "every citation is
computed by `locate_evidence`, never hand-written" instruction
(`runtime/agents/kubernetes-migration-analyzer.md:276-301`). Every citation
in all 3 reports — including the correct `Dockerfile:17`/`:21` ones above —
was therefore hand-written from `read` output, the exact bypass the
enforcement rule exists to prevent, and nothing in `validate_report.py` or
the harness catches it: a report can pass with zero `locate_evidence` calls
and any number of `근거:` references. This matches VS-023's own precedent —
its causal check separately found one inaccurate citation
(`package.json:10`) was hand-written from a `read` output rather than
`locate_evidence`-computed, which is what motivated the enforcement rule in
the first place.

This reproduction cannot settle the original question (it shows hand-writing
*can* still happen and still be accurate, not what happened in the specific
interactive run), and it used a different model
(`upstage/solar-pro2`) than the original run's `local-sglang/Qwen/Qwen3.6-35B-A3B-FP8`,
so provider-specific tool-call adherence is a real confound, stated plainly
rather than glossed over. n=3, one provider, one repository.

## Decision: HOLD — do not build the Phase 2 subset or the full five-tool set

Neither piece of evidence this ticket was opened to evaluate shows
`locate_evidence` itself confusing structurally similar files:

- The `INSERT INTO` finding is the tool working as designed (first
  matching line) on an under-specific `pattern` — a precision/tuning gap in
  the existing primitive, not a case for ecosystem-aware, filename-structural
  parsing. A `Dockerfile`/`docker-compose.yaml`-shaped parser would not have
  prevented it; it is about `INSERT INTO` matching the wrong *row*, not the
  wrong *file*.
- The wrong-file citation remains unattributed to `locate_evidence`
  specifically — no surviving trace shows a `locate_evidence` call whose
  `glob`/`pattern` matched `docker-compose.yaml` for a Dockerfile-scoped
  question — and the one fresh, trace-backed reproduction available (3/3
  Detailed runs, same repository and revision) did not reproduce it, while
  independently confirming that citations reaching a final report can
  bypass `locate_evidence` entirely under the current enforcement wording.

Building any of Phase 2's ecosystem-aware sensors (the full five-tool set,
or a narrower Dockerfile/Compose-only disambiguator) would not address
either actual gap this ticket found. A structural parser only helps once a
tool call is actually made with the tool computing the citation; the
demonstrated gap is upstream of that — the tool not being called at all,
which is an enforcement/verification problem, not a discovery-precision
problem five more tools would fix by construction.

This differs from `ADR-2026-08-07-003`'s own "consequences if narrower
Phase 1 confirmed" clause, which anticipated fabrication resurfacing as "the
agent picks a wrong `glob`/`content_pattern`" (a `locate_evidence`
*misuse* case). What this ticket instead found is the agent not invoking
`locate_evidence` at all — a different failure shape neither `ADR-2026-08-07-003`
nor VS-023's five-tool proposal targets, and one Phase 2 does not close: five
ecosystem-aware tools are still tools the agent would have to choose to call.

## Revisit signal (matching `ADR-2026-08-07-003`'s format)

Revisit this decision if a **trace-verified** case appears — not merely an
error visible in a final report — where a `locate_evidence` call itself,
with the `glob`/`pattern` the agent actually supplied, returns a
`found.reference` from a file other than the one the glob was evidently
scoped for (e.g., a `docker-compose.yaml` match returned for a
`glob: Dockerfile` or equivalently-scoped call). Until a trace shows that,
the evidence continues to point at (a) enforcement-compliance — whether the
agent calls `locate_evidence` at all, observed failing in this ticket's own
3/3 reproduction — and (b) match-precision within the existing primitive
(the `INSERT INTO` case), neither of which Phase 2's ecosystem-aware
tools would fix.

## Named follow-up (not this ticket's scope, not implemented here)

The zero-`locate_evidence`-calls finding is a new, more actionable gap than
either piece of evidence this ticket was opened to evaluate, and is
independent of the Phase 2 question: the "every citation must come from
`locate_evidence`" rule is prompt-only and mechanically unverified —
`validate_report.py` checks citation *shape* (a repository-relative
`path:line`), never citation *provenance* (whether a `locate_evidence` call
with a matching `reference` exists in the same session's trace). A
follow-up ticket could add that cross-check to the harness or
`report_contract.py` (reject/flag a report whose citation count is
positive but whose session made zero `locate_evidence` calls) without
touching discovery logic or building any new sensor tool. Naming this per
this project's change-scope rule rather than fixing it in this pass.

## Sample-size caveat

n=3 for the reproduction, one repository (`jpetstore-6`), one provider
(`upstage/solar-pro2`, not the original run's `local-sglang`). This is
enough to say the specific wrong-file bug did not trivially recur and to
surface the zero-tool-call gap, not enough to rule out `locate_evidence`
mis-matching a Dockerfile-shaped/Compose-shaped file under different
sampling, a different provider, or a different repository. If the named
follow-up (provenance verification) ships and *still* shows a genuine
`locate_evidence`-sourced wrong-file match, that would be exactly the
revisit signal above.
